# Syzygy pairing-logic gating — identity-team handoff (Keycloak)

> Generated by `scripts/keycloak_gating_setup.py --emit-handoff` from the
> same constants that drive the dev setup. Do not edit by hand — change
> the script and regenerate (`--emit-handoff docs/keycloak_gating_handoff.md`).

## What syzygy needs

While `LOGIC_GATING_ENABLED=true`, the app derives each user's
pairing-logic entitlements from the **access token** of its confidential
`syzygy` client (`syzygy/auth.py`; full behavior in
`docs/logic_gating_setup.md`, "How the app reads entitlements"). Three
claims, all optional — absent claims are fail-closed (no logics / no
non-consent entitlement):

| Claim | Shape | Meaning |
|---|---|---|
| `syzygy_logics` | JSON list of exact logic names, e.g. `["ARGOS", "DMP"]` | pairing logics the user may see |
| `syzygy_admin` | truthy value (reference shape `true`) | may trigger pairing and edit pairing logics |
| `syzygy_nonconsent` | JSON list of the user's group names (built-in mapper emits all groups; reference member shape `["DMP", "NONCONSENT"]`) | P3 consent gate: the `NONCONSENT` group name must appear in this list to see non-consent DMP samples (consent IS FALSE) |

Logic names must match the app's `pairing_logics` table **exactly,
case-sensitive**; unknown names are ignored server-side with a warning.

## Option (a) — realm groups (the reference shape)

Flat **top-level** groups, **exact case**, one per pairing logic, plus
the NONCONSENT entitlement group (P3, not a pairing logic):

| Group | Pairing logic |
|---|---|
| `ARGOS` | `ARGOS` |
| `DMP` | `DMP` |
| `HARMONY` | `HARMONY` |
| `ACCESS` | `ACCESS` |
| `TEMPO` | `TEMPO` |
| `NONCONSENT` | (entitlement, not a pairing logic — P3 consent gate) |

The mappers — all **built-in** types, no scripting — live on the
`syzygy` client's **dedicated client scope** (attached as a default
scope of the client). Every mapper must be stored under protocol
`openid-connect` (the scope's protocol): on Keycloak 26.8.1 a mapper
stored under any other protocol is **silently skipped at token
issuance**, and a PUT cannot change an existing mapper's protocol —
recreate it instead.

### Group mappers — one per logic group

- Protocol mapper: `oidc-group-membership-mapper`
- Placement: the `syzygy` client's **dedicated client scope**
- Protocol: `openid-connect`

All group mappers share this config — the claim values accumulate into the single `syzygy_logics` JSON list claim, so a user in any of the groups gets the list of ALL their logic-group memberships:

| Config key | Value |
|---|---|
| `claim.name` | `syzygy_logics` |
| `full.path` | `false` |
| `id.token.claim` | `false` |
| `access.token.claim` | `true` |
| `userinfo.token.claim` | `false` |

plus `claim.value` set to the exact group name — one mapper per group:

| Mapper | `claim.value` |
|---|---|
| `syzygy logics: ARGOS` | `ARGOS` |
| `syzygy logics: DMP` | `DMP` |
| `syzygy logics: HARMONY` | `HARMONY` |
| `syzygy logics: ACCESS` | `ACCESS` |
| `syzygy logics: TEMPO` | `TEMPO` |

### Admin mapper: `syzygy admin`

- Protocol mapper: `oidc-usermodel-attribute-mapper`
- Placement: the `syzygy` client's **dedicated client scope**
- Protocol: `openid-connect`

| Config key | Value |
|---|---|
| `user.attribute` | `syzygy_admin` |
| `claim.name` | `syzygy_admin` |
| `claim.value.type` | `Boolean` |
| `id.token.claim` | `false` |
| `access.token.claim` | `true` |
| `userinfo.token.claim` | `false` |

### Non-consent entitlement mapper (P3): `syzygy nonconsent: NONCONSENT`

- Protocol mapper: `oidc-group-membership-mapper`
- Placement: the `syzygy` client's **dedicated client scope**
- Protocol: `openid-connect`

Same built-in group-membership pattern as the logic family, feeding the `syzygy_nonconsent` claim. Important (verified live on Keycloak 26.8.1): the built-in mapper does NOT filter on its configured group — it emits ALL of the user's group names into the claim for any user who has at least one group. The claim is therefore present in most tokens, and the app derives the entitlement as `'NONCONSENT'` appearing in that list (NOT claim presence): a NONCONSENT member's list contains `'NONCONSENT'`, a non-member's does not. While gating is on, only users with the entitlement may see DMP-family samples whose consent is FALSE. (A NONCONSENT member also carries `NONCONSENT` inside `syzygy_logics` — the app ignores unknown logic names (warning only), so this is cosmetic, not an entitlement.)

| Config key | Value |
|---|---|
| `claim.name` | `syzygy_nonconsent` |
| `claim.value` | `NONCONSENT` |
| `full.path` | `false` |
| `id.token.claim` | `false` |
| `access.token.claim` | `true` |
| `userinfo.token.claim` | `false` |


User-profile requirement (Keycloak >= 26 hides the user *Attributes*
tab behind the User Profile feature): declare `syzygy_admin` as a
**managed attribute** (admin view/edit — `Syzygy logic admin`,
not required) and set the realm's **unmanaged attributes** policy to
**Admin can edit** (`ADMIN`).

Flow for the identity team: the users already exist (institutional
identity federation into our realm); merely **assign group membership**
for the logics each user should access, and set the `syzygy_admin`
attribute on logic admins. No app-side change.

## Option (b) — existing institutional claims, zero new groups

If the org realm already carries suitable claims, no groups or mappers
are needed at all: set the app's env vars to the org claim names (a
`.env` change — no code change):

| App env var | Default |
|---|---|
| `LOGIC_CLAIM_NAME` | `syzygy_logics` |
| `LOGIC_ADMIN_CLAIM` | `syzygy_admin` |
| `NONCONSENT_CLAIM` | `syzygy_nonconsent` |

The claim shapes must match the table above (exact-name JSON list /
truthy boolean) and the claims must ride in the **access token** of the
`syzygy` client. If the org claim shape differs (e.g. a group *path*
like `/syzygy/logic/argos` instead of an exact name), a transform is
required that no built-in mapper provides — see the JS-mapper appendix
in `docs/logic_gating_setup.md`.

## Minimum-privilege asks

- A **realm-admin** on the syzygy realm is sufficient — never a
  master-realm admin.
- Option (a) needs, on the syzygy realm: manage **groups**; manage
  protocol mappers on the `syzygy` client's dedicated scope; manage the
  realm **user profile** (the `syzygy_admin` attribute declaration +
  the unmanaged-attributes policy); and **group-membership assignment**
  on users.
- Option (b) needs **no realm permissions** — it is an app-side
  configuration change only.

## Deferred

- **Brokered-realm group assignment**: end-to-end testing of assigning
  federated (brokered) users to the groups above is **DEFERRED** until
  the org realm exists. The shape above was built and verified on the
  dev compose Keycloak (26.8.1), where the same mappers/claims issue
  for directly-created users; brokered users were not yet testable.

## Reproduce on dev

    .venv/bin/python scripts/keycloak_gating_setup.py \
        --realm master --username admin --password admin \
        --personas --allow-user-creation

The script is idempotent (run twice, same result) and ends by printing
each dev persona's decoded access-token claims.
